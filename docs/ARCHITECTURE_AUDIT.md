# DockSense AI — รายงานตรวจสอบสถาปัตยกรรมและแผนดำเนินการ

ตรวจเมื่อ 2026-11-09 จากซอร์สใน repo, Supabase โปรเจกต์ `dhqvdbdqhcbymqvhpqop` (ตาราง, Edge Functions, security advisors) และรูปอุปกรณ์จริงที่เจ้าของส่งมา
ยังไม่มีการเปลี่ยนสถาปัตยกรรมใหญ่ รอการตัดสินใจในหัวข้อ 8

สัญลักษณ์: ✅ ใช้งานจริงและยืนยันแล้ว · 🟡 เขียนและ deploy แล้วแต่ยังไม่ยืนยันบนหน้างานจริง · ❌ ยังไม่มี · ⚠️ มีปัญหา

## 1. สถาปัตยกรรมปัจจุบัน

```
มือถือ / ESP32-CAM ──HTTPS──▶ Supabase Edge Function camera-ingest ──▶ ocr-plate (Gemini) ──▶ Postgres + Storage
                                                                  └─▶ notify-visit ──▶ Telegram
Telegram ◀──webhook──▶ Edge Function telegram-bot ──▶ Postgres
เว็บ (HTML สแตติก บน Vercel, ไม่มี build) ──▶ Supabase (Auth, RLS, Realtime, Storage)
```

ไม่มีเซิร์ฟเวอร์ Python ในระบบ งาน AI ทั้งหมดเรียก Gemini API (โควตาฟรี) ผ่าน Edge Function

## 5. ความปลอดภัย (จาก Supabase advisors)

- ⚠️ Views `visit_details`, `camera_status` เป็น SECURITY DEFINER (ระดับ ERROR) ต้องตรวจว่าเปิดข้อมูลข้ามสิทธิ์หรือไม่ก่อนแก้
- ⚠️ ฟังก์ชัน SECURITY DEFINER 6 ตัวที่ผู้ล็อกอินเรียกได้ (`camera_snap`, `camera_watch`, `confirm_capture`, `reject_capture`, `request_live`, `app_role`) ต้องตรวจว่าแต่ละตัวเช็กสิทธิ์ในตัวเอง
- ⚠️ `ds_lev` ไม่ได้ตั้ง search_path · ⚠️ ยังไม่เปิดตรวจรหัสผ่านที่รั่ว (ตั้งในแดชบอร์ด Auth)
- `camera-ingest` และ `telegram-bot` ปิด verify_jwt โดยตั้งใจ ใช้คีย์อุปกรณ์/ secret ของ webhook แทน: ต้องเพิ่ม rate limit ต่อคีย์ที่เป็นของจริง ตอนนี้มีแค่ cooldown ในหน่วยความจำของฟังก์ชัน (รีเซ็ตเมื่อฟังก์ชันเริ่มใหม่)
- ยังไม่พบคีย์/โทเคนในซอร์ส repo; secrets อยู่ที่ Supabase

## 6. ข้อค้นพบจากรูปอุปกรณ์จริง

1. **รีเลย์ตัวขวาเป็นคอยล์ 12V (JQC3F-12VDC-C)** ใช้กับไฟ 5V ไม่ได้ผล ใช้ตัวซ้าย (SRD-05VDC-SL-C) เท่านั้น ตัวซ้ายและตัวขวา **ลำดับขาคนละแบบ** (ซ้าย IN GND VCC / ขวา VCC GND IN) ต้องดูตัวหนังสือบนบอร์ดทุกครั้ง ยังไม่ทราบว่าตัวซ้ายทริกด้วยระดับ HIGH หรือ LOW ต้องทดสอบบนโต๊ะ
2. **บอร์ดขยายสีม่วง** มีจัมเปอร์เลือก 5V/3.3V ให้แถว V สีแดง ต้องตั้งเป็น 5V สำหรับเซอร์โว รีเลย์ HC-SR04 และมีช่องไฟเข้า 3 ทาง (USB-C, micro-USB, แจ็ก DC 6.5–16V) ห้ามจ่ายไฟพร้อมกันสองทาง
3. **โมดูล IR (HW-201)** ขาเรียง OUT GND VCC ตรงกับคู่มือ ใช้ไฟ 3.3V ได้
4. **ESP32-CAM** วางบนฐาน micro-USB มีไฟแฟลชขาวบนบอร์ด (GPIO4) เลนส์หมุนปรับโฟกัสได้
5. **ไฟเลี้ยง**: ภาระรวมโดยประมาณ (ESP32-CAM ช่วงส่งภาพ + DevKit Wi-Fi + HC-SR04 + IR + รีเลย์) ใกล้ 1A ซึ่งเต็มพิกัดของแบงก์ 5V/1A ใช้อะแดปเตอร์ 5V/2A สำหรับระบบถาวร ค่าตัวเลขเป็นการประมาณ ควรวัดด้วยเครื่องวัดกระแส USB
6. ตัวแปลงไฟ LM2596 ลดแรงดันได้อย่างเดียว ไม่จำเป็นเมื่อใช้ไฟ USB 5V

## 7. สถาปัตยกรรมที่แนะนำ (ยังไม่ลงมือ)

หลักการ: เพิ่มของใหม่ข้างของเดิม ไม่รื้อ

- **ประตูรับข้อมูลของ ESP32 ยังเป็น Supabase Edge Function** (ESP32 ต่อ HTTPS ตรง ไม่มี cold start ไม่มีค่าเซิร์ฟเวอร์)
- **Python/FastAPI เป็น "OCR worker" เสริม** รับภาพจาก Edge Function เมื่อมี worker พร้อม ถ้าไม่ตอบก็ถอยกลับไปใช้ Gemini เหมือนเดิม จึงไม่ทำให้ระบบล่มเมื่อ worker หลับ
- **เว็บยังเป็นสแตติกบน Vercel**; โมเดล AI และ FastAPI ไม่รันบน Vercel
- **ตัวเลือกโฮสต์ Python แบบไม่มีค่าใช้จ่าย** (ต้องตรวจเงื่อนไขล่าสุดก่อนเลือก ผมยังไม่ได้ตรวจ): Hugging Face Spaces (Docker, CPU), Render แบบฟรี (หลับเมื่อไม่ใช้งาน แรมน้อย), Oracle Cloud Always Free (ต้องยืนยันบัตร), หรือคอมของคุณเอง ถ้าต้องการอ่านสดเร็วๆ ทุกครั้ง ตัวเลือกที่หลับได้ไม่เหมาะ
- **ESP32 สองบอร์ด**: แนะนำคงสายสัญญาณ 2 เส้นไว้ (DevKit สั่งกล้อง) และเพิ่มให้ DevKit รายงานเหตุการณ์ผ่าน Wi-Fi เหตุผล: ทำงานได้แม้อินเทอร์เน็ตหรือ backend ล่ม ไม่มีความหน่วงจากเครือข่ายตอนสั่งถ่าย พรอมต์ห้ามเชื่อมสายตรงถ้าไม่มีเหตุผลทางเทคนิค จึงต้องการคำตัดสินจากเจ้าของ (ข้อ 8-ข)
- **ข้อมูล**: เพิ่มตารางด้วย migration แบบ idempotent: `detection_sessions`, `recognition_results` (ผลดิบ/ผลปรับ/ความเชื่อมั่น/เวลาประมวลผล), `device_events`, `notification_logs`, `ai_metrics` ไม่แตะตารางเดิม

## 8. คำถามที่ต้องตัดสินใจก่อนลงมือ

ก. งบ: ยอมให้มี Python worker บนบริการฟรีที่อาจหลับ/ช้า หรือคงใช้ Gemini เป็นหลักไปก่อน แล้วเพิ่ม worker ภายหลัง? (แนะนำ: ทำตามลำดับ ให้ Gemini เป็นหลักจนกว่าจะวัดผลเทียบ)
ข. สาย DevKit↔กล้อง: คงสายสัญญาณ 2 เส้น (แนะนำ) หรือใช้ Wi-Fi ล้วนตามพรอมต์?
ค. ชุดภาพทดสอบ: ต้องมีภาพทะเบียนรถจริงพร้อมเฉลยอย่างน้อย 50–100 ภาพ (กลางวัน/กลางคืน/มุมเอียง/เบลอ) ไม่มีชุดนี้ จะเทียบ PaddleOCR/EasyOCR/Gemini ไม่ได้ และห้ามอ้างตัวเลขความแม่นยำ
ง. ข้อความพรอมต์ถูกตัดที่ Part 9-D ("restrict it to authorized dat…") ช่วยส่งส่วนที่เหลือ (Part 10 เป็นต้นไป) มาให้ครบ
จ. บอทใช้ LLM เข้าใจภาษาหรือคงแบบกฎ? LLM ใช้โควตา Gemini ร่วมกับการอ่านป้าย

## 9. แผนทำงาน (เรียงตามความเสี่ยงต่ำไปสูง)

1. **ยืนยันฮาร์ดแวร์บนโต๊ะ** (ไม่แตะโค้ด): ไฟเลี้ยง วัดแรงดัน, HC-SR04 พร้อมตัวแบ่งแรงดัน, รีเลย์ตัวซ้าย (หาระดับทริก), ESP32-CAM ส่งภาพถึง `camera-ingest`
2. **ความปลอดภัยฐานข้อมูล**: ตรวจ views/ฟังก์ชัน SECURITY DEFINER ทีละตัวพร้อมทดสอบ แล้วแก้
3. **Migration ตารางใหม่** (sessions, results, device_events, notification_logs, metrics) และให้ `camera-ingest` เขียนผลดิบ ความเชื่อมั่น เวลาประมวลผล
4. **เฟิร์มแวร์ DevKit** เพิ่ม LED 3 สี รายงานเหตุการณ์/สุขภาพผ่าน Wi-Fi แบบ non-blocking (ไม่ใช้ delay ยาว)
5. **ชุดทดสอบ + สคริปต์วัดผล** รอภาพทดสอบจากข้อ ค.
6. **Python OCR worker** (ถ้าผลวัดชี้ว่าคุ้ม) พร้อมอ่านหลายเฟรมและโหวต
7. **บอท**: เพิ่มคำสั่งแยกและถามสถานะอุปกรณ์/AI จากข้อมูลจริง
